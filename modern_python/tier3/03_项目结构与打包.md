# T3-3 项目结构与打包

> 收尾主题：把代码从"一堆脚本"变成"可安装、可分发、可入口调用的包"。

## 1. src 布局 vs flat 布局

```
# src 布局（现代默认）
modern_tools/
├── pyproject.toml
├── src/
│   └── modern_tools/
│       ├── __init__.py
│       └── cli.py
└── tests/
    └── test_cli.py

# flat 布局（老式）
modern_tools/
├── pyproject.toml
├── modern_tools/
│   └── cli.py
└── tests/
```

src 布局的核心价值：`tests/` 运行时 import 的是**安装后的包**，不是 cwd 下的源码目录——杜绝"在我机器上能跑，因为恰好 cwd 里有一份"的侥幸。flat 布局下测试永远在测 cwd 里的那一份，装出来的包和它不一致时问题被推迟到部署时才炸。

## 2. pyproject.toml 的打包面

```toml
[build-system]                      # 打包后端：谁把源码变成 wheel
requires = ["hatchling"]
build-backend = "hatchling.build"

[project]
name = "modern-tools"               # PyPI 名（连字符）；导入名 modern_tools
version = "0.1.0"
requires-python = ">=3.12"
dependencies = []

[project.scripts]                   # 入口点：安装后生成同名命令
modern-tools = "modern_tools.cli:main"
```

Java 对照：`[project]` ≈ pom 坐标，`[build-system]` ≈ 选 maven 还是 gradle，`[project.scripts]` ≈ appassembler/exec 插件配的可执行入口——但它是**安装包自带的**，装完即有命令。

## 3. 构建、检查、发布

```bash
uv build                            # 产出 dist/*.whl + dist/*.tar.gz
uv publish                          # 发布到 PyPI（或私有源，--index-url 指定）
```

- **wheel**：预编译分发，装得快，`uv pip install` 的默认选择。
- **sdist（.tar.gz）**：源码分发，后端安装时现场构建——总会有，wheel 才是你的交付物。

发布前自检：换个干净 venv 安装 wheel，跑入口命令（练习 1 就是干这个的）。

## 4. 入口与 `__main__`

```python
# cli.py
def main() -> None:
    ...argparse 解析...

if __name__ == "__main__":          # 直接 python -m modern_tools.cli 时生效
    main()
```

```python
# modern_tools/__main__.py —— 让 python -m modern_tools 整包可执行
from modern_tools.cli import main
main()
```

两种入口并存：`[project.scripts]` 面向安装后的用户，`python -m` 面向开发和调试。`if __name__ == "__main__":` 的语义：只有该模块被**当作脚本**运行时为真，被 import 时为假——这就是练习文件里"演示代码"的合法位置。

## 5. 模块内组织惯例

- `__init__.py` 做 re-export + `__all__`（T3-1 第 5 节），外部只 import 门面。
- `cli.py` / `core.py` / `config.py` 的薄分层：CLI 只做解析和调度，逻辑在 core（可测试性——CLI 层保持 0% 覆盖率也可接受，core 必须 90%+）。
- 版本号单一来源：`__init__.py` 里 `__version__ = "0.1.0"`，pyproject 用 hatchling 的 `tool.hatch.version` 从这读，改一处即可。
