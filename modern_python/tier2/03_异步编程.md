# T2-3 异步编程

> 前置：T2-2 的 `except*`。这是和 Java 差异最大的并发模型，先纠正心智模型再写代码。

## 1. 心智模型：协作式调度，不是隐藏阻塞

| | Java 虚拟线程 | Python asyncio |
|---|---|---|
| 写法 | 同步阻塞代码，平台自动挂起 | 必须显式 `async`/`await` |
| 让出时机 | 阻塞调用时自动 | **只在 `await` 处**，代码主动让出 |
| 传染性 | 无，同步异步互通 | async 函数只能被 async 调用（"函数变色"） |
| 调度 | 抢占式 | 协作式：单个协程不放权，全体干等 |

两条由此推导的铁律：

1. **async 函数里出现一次阻塞调用（`requests.get`、`time.sleep`、重计算），整个事件循环停摆**——不是慢，是所有协程全停。
2. 忘了 `await` 只是拿到一个 coroutine 对象，什么都不会发生（甚至收到 warning 都算你幸运）。

## 2. 基础设施

```python
import asyncio

async def fetch(name: str) -> str:
    await asyncio.sleep(1)        # 模拟 IO；真实 IO 用 httpx 的 await client.get(...)
    return f"{name} done"

async def main() -> None:
    results = await asyncio.gather(fetch("a"), fetch("b"), fetch("c"))
    print(results)                # 三个一起跑，总耗时 ~1s 而不是 3s

asyncio.run(main())               # 程序唯一的同步入口
```

三个层次要分清：

- **coroutine 函数**：`async def` 定义的，调用它**不执行**，返回 coroutine 对象。
- **await**：执行到完成并取回结果，期间事件循环可以去跑别的协程。
- **Task**：`asyncio.create_task(coro)` 把协程注册进事件循环"现在就开始跑"，`await task` 只是取结果。想并发就必须 create_task 或 gather，**顺序 await 两个协程是串行**——这是新手第一大坑：

```python
await fetch("a")   # 1s
await fetch("b")   # 又 1s   ← 这不是并发！总耗时 2s
```

## 3. TaskGroup：结构化并发（3.11+，新代码首选）

```python
async def main() -> None:
    results: dict[str, str] = {}
    async with asyncio.TaskGroup() as tg:      # 退出块 = 全部完成或全部取消
        t1 = tg.create_task(fetch("a"))
        t2 = tg.create_task(fetch("b"))
    print(t1.result(), t2.result())            # 块外保证都已完成
```

与 `gather` 的关键区别在**失败语义**：组内任一任务抛异常，其余任务被取消，`async with` 块抛 `ExceptionGroup`（配 T2-2 的 `except*` 捕获）。对应 Java 正在演进的 structured concurrency——**并发的生命周期不会逃出词法作用域**，没有孤儿任务。

`gather` 保留用于两个场景：需要保序收集全部结果（`return_exceptions=True` 时"谁失败都继续"）。

## 4. httpx：同步异步统一 API

```python
import httpx

async def fetch_all(urls: list[str]) -> list[int]:
    sizes = []
    async with httpx.AsyncClient(timeout=30) as client:   # 复用连接池，别每次新建
        for url in urls:                                  # 演示用；并发写法见练习
            resp = await client.get(url)
            sizes.append(len(resp.content))
    return sizes
```

对照 `requests`：API 几乎一样，多了 `await`；一个库通吃同步异步，不用学两套。**requests 在 async 函数里是禁忌**（见铁律 1）。

## 5. 并发选型表（GIL 视角）

| 任务特征 | 方案 | 理由 |
|----------|------|------|
| 网络/磁盘等待为主（爬虫、批量 API 调用） | asyncio | 单线程扛上千并发等待，切换成本极低 |
| CPU 密集（数值计算、图像处理） | NumPy 向量化 / 多进程 | GIL 让 asyncio 和线程都白搭；向量化把循环下沉到 C |
| async 里必须调阻塞库 | `asyncio.to_thread(blocking_fn)` | 扔线程池，别堵事件循环 |
| 3.13+ 自由线程 | 观望 | 实验性，生态适配中 |

GIL 一句话：同一时刻只有一个线程在执行 Python 字节码，所以**线程不解决 CPU 密集**（IO 等待时 GIL 会释放，所以线程对 IO 密集也有效，但 asyncio 更省）。

## 6. 常见坑清单

- 顺序 `await` 当成并发（上文第一大坑）
- async 函数里用 `requests`/`time.sleep`/重 CPU 计算
- 忘 `await`，协程根本没跑
- 每次请求新建 `AsyncClient`（无连接复用）
- 在事件循环已运行的环境（如 Jupyter）里调 `asyncio.run`——Jupyter 里直接 `await fetch()` 即可
