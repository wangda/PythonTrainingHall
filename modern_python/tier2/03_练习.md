## 题 1：并发抓取基线

起始代码：`exercises/t2_3/serial_fetch.py`——串行抓 10 个 URL，先跑出基线耗时。

要求（改写为 `exercises/t2_3/concurrent_fetch.py`）：

1. 用 `httpx.AsyncClient` + `asyncio.gather` 并发抓同样的 10 个 URL。
2. 两个版本各计时（`time.perf_counter()`），耗时表写进文件顶部注释。
3. 故意写一个"顺序 await 十连"的错误版本（`await client.get` 循环）计时——三种耗时应呈现 `10T / T / T` 量级关系，这就是并发是否生效的直接证据。
4. 共享一个 `AsyncClient`（连接复用），禁止循环内新建。

**验收标准**：并发版耗时 ≈ 串行版 1/8 以下（10 个请求）；注释里的三种耗时数据完整。

## 题 2：TaskGroup 的失败语义

改写为 `exercises/t2_3/taskgroup_fetch.py`：

1. 用 `TaskGroup` 重做题 1。
2. 让第 4 个 URL 的处理协程必然抛 `ValueError`（手动 raise，模拟解析失败）。
3. 观察并注释：其余任务是否被取消？`async with` 退出时抛的是什么类型？用 `except* ValueError as eg` 捕获，打印 `eg.exceptions`。
4. 补一个 `gather(..., return_exceptions=True)` 版本做对照：同样的故障场景下两者各自"谁活谁死"，差异写进注释。
5. 结论一句话：什么业务场景该选 TaskGroup，什么场景 `gather(return_exceptions=True)` 反而正确。

**验收标准**：能演示"一损俱损"（TaskGroup）和"各跑各的"（gather）两种行为；结论注释到位。

## 题 3：CPU 密集实验——asyncio 的边界

起始代码：`exercises/t2_3/cpu_bound.py`——两两距离平方和的 O(n²) 朴素循环（200 个点 ≈ 2 万对）。

要求（写成 `exercises/t2_3/cpu_experiment.py`）：

1. 基线：朴素 for 版本计时。
2. 用 `asyncio.gather` 跑 **4 份**同样的纯计算任务，计时。预期：总耗时 ≈ 4 × 单份——用数据验证 GIL 下的"伪并发"。
3. NumPy 向量化版（广播：`diff = pos[:, None, :] - pos[None, :, :]`，掩码掉自身对），计时，记录加速比。
4. 进阶（可选）：`ProcessPoolExecutor` 版计时，与 NumPy 版对比并注释原因（进程开销 vs 单次计算规模）。

**验收标准**：四种方案耗时表；结论注释能回答——**什么任务不该用 asyncio**（README 里程碑要求），以及本项目哪些代码（提示：`numpy_train/`）属于该结论的适用范围。
