## 1. 项目目标与产出

### 1.1 为什么要做这个项目

模块 1 你练的是**工程流程**：配置分离、单元测试、CLI 入口、模型包。这套骨架本项目原样复用——所以如果模块 1 的项目你做扎实了，本项目的"工程"部分零新增成本。真正的增量在数据维度：

- **图像数据**：输入不再是表格里 8 个语义明确的特征，而是 8×8 = 64（或 28×28 = 784）个像素。像素没有"收入中位数"那样的业务含义，怎么把它变成模型能吃的特征矩阵，是本项目的第一课；
- **多分类**：房价预测输出一个数，本项目输出 10 个类别里的一个。前置文档 §5 的 softmax 在这里从公式变成 `model.predict_proba` 的真实输出；
- **概率输出**：预测不再只是"是几"，而是"是几、多确定"。top-3 概率能告诉你模型在 4 和 9 之间有多纠结——这是回归给不了的视角。

### 1.2 产出物

做完这个项目，你将拥有：

1. 一个双数据源的训练流水线：`config.yaml` 里一行切换 digits / mnist；

3. 一张混淆矩阵热力图 + 一组分类指标（accuracy / macro P / R / F1）；
4. 对"预处理必须在预测时复现"这件事的肌肉记忆（你会亲手踩一次反相的坑）。

## 2. 数据集：digits 与 MNIST

### 2.1 两个数据集对比

| 属性 | digits | MNIST |
|---|---|---|
| 样本数 | 1797 | 70000 |
| 分辨率 | 8×8 = 64 像素 | 28×28 = 784 像素 |
| 像素范围 | 0 ~ **16**（不是 255！） | 0 ~ 255 |
| 获取方式 | sklearn 内置 `load_digits()`，零下载 | `fetch_openml("mnist_784")`，首次下载后缓存 npz（约 20MB） |
| 定位 | 秒级训练，快速验证流程 | 真实规模，最终成绩单 |

为什么要双数据源？**快速迭代**。调通流程时每一秒等待都是注意力流失——digits 从训练到评估全程 3 秒左右，错了立刻重来；流程确认无误后，一行 config 切到 mnist 跑真实规模。这是工程上的标准做法：小数据调管道，大数据出成绩。

加载并亲眼看一眼（`data/download.py` 已实现，直接跑）：

```python
from data.download import load_dataset

X, y, meta = load_dataset(config)   # config["data"]["dataset"] = "digits"
print(X.shape)                      # (1797, 8, 8) —— 注意是三维，还没展平
print(meta)                         # {'dataset': 'digits', 'image_shape': (8, 8),
                                    #  'pixel_max': 16.0, 'classes': [0..9]}
```

meta 里的 `pixel_max` 是本项目最重要的元信息：**归一化系数跟着数据集走**，digits 除 16，mnist 除 255。它会随模型一起打包保存，预测时靠它复现预处理（§3.3）。

### 2.2 看一看数据长什么样

图像数据的第一步永远是**用眼睛看**。下面这段代码实际跑过，输出存为 `reports/figures/digits_samples.png`：

```python
import matplotlib.pyplot as plt
from sklearn.datasets import load_digits

digits = load_digits()
fig, axes = plt.subplots(2, 5, figsize=(8, 3.5))
for ax, i in zip(axes.flat, range(10)):
    ax.imshow(digits.images[i], cmap="gray")   # 8×8 灰度图
    ax.set_title(f"标签: {digits.target[i]}")
    ax.axis("off")
```

![digits 样例](../../projects/mnist_classification/reports/figures/digits_samples.png)

两个直观感受，先记住：

1. **8×8 真的很糊**——你能认出它们，但有些数字已经勉强（比如 1 和 7 的区分全看那一横）。这解释了后面混淆矩阵里的误判；
2. **黑底白字**：背景是 0（黑），笔画是亮值（白）。这个约定决定了 predict.py 的 `--invert` 为什么存在（§7.2）。

### 2.3 为什么要展平

`load_digits()` 给的 X 是三维的 `(1797, 8, 8)`：每张图是 8 行 8 列的像素网格。但 `LogisticRegression` 只吃二维的 `(n_samples, n_features)`——**线性模型没有空间概念**，对它来说"第 3 行第 4 列的像素"和"第 4 行第 3 列的像素"只是两个编号不同的特征，相邻与否它根本不知道、也不需要知道。

所以展平就是一道简单的变形：`(1797, 8, 8) → reshape → (1797, 64)`。64 个像素 = 64 个特征，和模块 1 的 8 个特征在模型眼里没有任何区别——只是维度高了。

> 代价也要知道：展平**丢弃了空间结构**（哪些像素相邻）。对 8×8 的糊图无所谓，对 28×28 以上的真实图像，这个损失就是线性模型的天花板——这正是模块 5 CNN 要解决的问题（§6 展开）。

### 2.4 类别分布：基本均衡，所以准确率够用

digits 全集 10 个类别的样本数（实测）：

```
[178 182 177 183 181 182 181 179 174 180]
```

每类都在 174~183 之间，最大最小相差不到 5%——这是**教科书级的类别均衡**。这意味着：

- **准确率（accuracy）是够用的总指标**。前置文档 §7 警告过：类别不平衡时准确率会说谎（98.9% 健康人的体检数据，全猜"健康"也有 98.9% 准确率）。这里每类各占约 10%，没有这个问题；
- 但宏平均（macro）指标仍要看：它给每个类别同等权重，能暴露"模型在少数难类上翻车"的情况——digits 里类别 1 的 recall 只有 0.83，总准确率 0.96 掩盖了这一点（§5 任务 2 会细看）。

## 3. 工程化：复用模块 1 的骨架，只讲差异点

七文件骨架（config / download / features / model / train / evaluate / predict）的职责划分、配置与代码分离的理由、工厂模式——这些在《02-房价预测项目文档.md》§3 已经讲透，不再重复。这里只讲本项目的三个**差异点**。

### 3.1 差异一：无状态归一化，不存在数据泄漏

模块 1 的 `split_and_scale` 是全项目最危险的函数：StandardScaler 要从训练集学出均值/方差，顺序错了就是数据泄漏。本项目的归一化完全不同：

```python
# 像素归一化：除以一个先验常数（数据集固有的像素上限）
X_normalized = X / meta["pixel_max"]    # digits: 16，mnist: 255
```

它是**无状态**的——不从数据里统计任何量，每个样本独立变换。先除后除、全量除还是单条除，结果逐元素一致。所以：

- 不存在"先划分还是先 fit"的顺序陷阱，`split_data` 干完划分就结束了，没有 scaler 对象要保存；
- `tests/test_features.py` 里的防泄漏测试换了一种查法：`test_归一化_无状态所以无泄漏` 断言**单条处理和整批处理结果一致**——StandardScaler 永远过不了这条。

但"无状态"不等于"无坑"：系数来自 meta 而不是写死的 255，搞错就是静默出错（§7.1）。

### 3.2 差异二：模型包里存的是数据集元信息

模块 1 的模型包是 `{model, scaler, feature_names}`。本项目没有 scaler，取而代之的是：

```python
{"model": model,
 "meta": {"dataset": "digits", "image_shape": (8, 8),
          "pixel_max": 16.0, "classes": [0..9], "normalize": True}}
```

预测一张外部图片时，`predict.py` 需要回答：图片该是几乘几的？（`image_shape` 校验尺寸）；像素该除以几？（`pixel_max` 归一化）；输出的概率对应哪些类别？（`classes`）。这些全是**训练时的约定**，必须随模型一起走——少任何一样，预测就是错的。思想和模块 1 完全一致：**模型包 = 模型 + 复现预处理所需的一切**，只是"一切"的内容变了。

### 3.3 差异三：predict 的输入是图片

模块 1 的 predict 吃 8 个逗号分隔的数；本项目的 predict 吃一张 PNG 图片（或一行 64/784 个像素值的 csv）。多出来的整条预处理链：读图 → 转灰度 → 校验尺寸 → （可选）反相 → 展平 → 归一化——每一步都要和训练时对齐，而它们全部是无状态变换，所以 predict.py 不依赖 features.py，靠 meta 自包含完成。

## 4. 标准 ML Pipeline 五步走

| 步骤 | 干什么 | 本项目落点 |
|---|---|---|
| ① 加载数据 | 获取原始数据并缓存 | `data/download.py` 的 `load_dataset(config)`（双数据源统一接口） |

### 任务 4：predict.py 推理实战

训练完成后，拿真实图片走一遍推理。没有手绘条件也没关系——下面是本环境实测的一次完整演示：从测试集取一张真实标签为 5 的图，存成 PNG，分别走"黑底白字"和"白底黑字"两条路：

```bash
# ① 黑底白字（与训练数据同分布）：正确
../../../.venv/bin/python predict.py --input digit_8x8.png
# 样本 0: 预测 = 5（置信度 86.16%）
#     类别 5: 86.16%
#     类别 9: 12.33%
#     类别 8: 0.70%

# ② 同一张图反相成白底黑字，不加 --invert：翻车现场
../../../.venv/bin/python predict.py --input digit_8x8_inverted.png
# 样本 0: 预测 = 2（置信度 41.31%）   ← 模型在胡猜
#     类别 2: 41.31%
#     类别 4: 37.72%
#     类别 7: 18.89%

# ③ 加上 --invert：恢复正确
../../../.venv/bin/python predict.py --input digit_8x8_inverted.png --invert
# 样本 0: 预测 = 5（置信度 86.27%）
```

三个要点：

1. **top-3 概率在讲故事**：正确预测里 5 vs 9 是 86% vs 12%——模型确实在纠结（digits 的 5 和 9 都像一竖带个圈）；翻车预测里最高置信度只有 41%，前三名 2/4/7 互不相让——**低置信度本身就是一种报警信号**（前置文档 §6：概率不是结论，是依据）。
2. **预处理必须复现**：同一张图，预处理错一步（没反相），预测从 86% 正确变成 41% 胡猜，而且**不报错**——这是最危险的静默错误。
3. csv 输入路径也实测过（同一像素的 csv 与 PNG 预测一致：86.11% vs 86.16%，差异来自 PNG 量化的舍入），两条输入路径都通。

## 6. 特征工程提示：本项目的"特征"就是像素

模块 1 的特征工程是造新特征（BedroomRatio 等）；本项目的"特征工程"朴素得多——**64/784 个像素就是全部特征**，工程上只有两件事：展平（§2.3）和归一化（§3.1）。归一化为什么必须做：像素 0~16/0~255 的量纲会让梯度下降在不同特征上步长失衡（前置文档 §4 的特征尺度问题），压到 [0, 1] 后 lbfgs 收敛明显更快更稳。

想做更多？方向给你，不实现：

- **居中裁剪/去边框**：digits 的四边几乎全是 0，裁掉后有效信息密度更高；
- **HOG（方向梯度直方图）**：统计局部边缘方向的分布，把"像素"翻译成"笔画的走向"，是 CNN 出现之前手写数字识别的标准特征；
- **数据增强**：随机平移/旋转/加噪，凭空造出更多训练样本。

但要知道一个历史事实：**图像任务的特征工程，后来被 CNN 整体取代了**。上面三个方向全是人类在用领域知识"猜"什么特征有用；CNN 直接让模型自己从像素里学特征，效果碾压一切手工设计。模块 5 你会亲手验证这件事——到时回看本项目 `flatten_images` 里"丢弃空间结构"的注释，你会明白那就是线性模型的天花板所在。

## 7. 常见坑（每个都值一次报错）

### 7.1 归一化系数搞错：digits 是 0~16，不是 0~255

```python
# ❌ 错误：拍脑袋除以 255
X_normalized = X / 255        # digits 的像素被压到 [0, 0.063]，特征尺度缩水 16 倍

# ✅ 正确：系数跟着数据集走
X_normalized = X / meta["pixel_max"]   # digits: 16.0，mnist: 255.0
```

这个错**不报错、不崩溃**，模型照样训练，只是特征尺度不对、精度受损——典型的静默错误。所以 `pixel_max` 必须由 `data/download.py` 随数据集给出（meta），而不是在 features.py 里写死。`tests/test_features.py` 的 `test_归一化_系数取自meta的pixel_max` 专查这个：同一个像素值 16，digits 下应归一化为 1.0，mnist 下应为 16/255。

### 7.2 手绘图忘记反相

训练数据是**黑底白字**（背景 0，笔画亮）。你用画图软件写的数字大概率是**白底黑字**——直接喂进去等于让模型看一张"底片反过来"的图，预测会离谱（§5 任务 4 的实测：5 被认成 2）。`predict.py --invert` 就是干这个的。判断方法：看图时背景是白的，就加 `--invert`。

### 7.3 图片尺寸不对

digits 训练的模型只吃 8×8，mnist 的只吃 28×28。`predict.py` 会拿 meta["image_shape"] 校验，尺寸不符直接报清晰的错误：

```
ValueError: 图片尺寸应为 8×8（训练数据集 digits 的规格），收到 (100, 100)。请先缩放到 8×8 再预测。
```

别试图绕过校验"让模型将就一下"——输入维度都对不上，矩阵乘法直接炸；硬 resize 到一个模型没见过的分布，预测同样没有意义。

### 7.4 类别不平衡时别看准确率

本项目类别均衡（§2.4），accuracy 是诚实的。但要记住前置文档 §7 的警告什么时候生效：如果某天数据变成 95% 是 1、5% 是其他数字，accuracy 0.95 的模型可能除了 1 什么都不会认。那时候宏平均 P/R/F1 和混淆矩阵才是主指标——这正是 evaluate.py 把它们四个一起输出的原因，看报告时养成四个一起看、再对一遍混淆矩阵的习惯。

### 7.5 fetch_openml 下载慢/失败

mnist 数据托管在 OpenML，国内网络可能极慢甚至挂起（本环境实测：连接能建立但数据下载挂起，两次 300 秒超时无数据返回；最终改用 MNIST 官方 IDX 镜像构建缓存，见 §5 任务 3）。对策已经内建在工程里：

1. **缓存策略**：下载一次，`data/raw/mnist.npz` 永久复用（npz 压缩格式约 20MB；千万别存 csv——70000×784 的 csv 有几百 MB）。本仓库已预置该缓存，`load_dataset` 会直接命中；
2. **digits 兜底**：网络不通时 digits 全流程不受影响，先在小数据上把流程和代码调对，网络恢复后再切 mnist——这正是双数据源设计的意义。
